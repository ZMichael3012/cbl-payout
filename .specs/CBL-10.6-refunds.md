# CBL-10.6. Возвраты (refunds) как частный случай выплаты

| Поле | Значение |
| :-- | :-- |
| Эпик | E10, Payout/Refund Service (Saga) |
| Репозиторий | `cbl-payout` (контрактный вход - `cbl-protos` 5b3d1e0) |
| Размер | M |
| Волна и параллельная группа | W2-PAYOUT |
| Зависит от | 10.2, 10.5 |
| Версия контрактов | `cbl-protos@cf-2.1` (аддитивные поля возвратов, 5295373) |
| Статус | done, ревью закрыто |

## 1. Контекст и цель

Возврат - частный случай выплаты (`CBL-000`, раздел 5; `CBL-003`, раздел 2:
`POST /v1/refunds` с `invoice_id`, `amount`, `destination_address`): тот же
путь саги (резерв -> команда -> результат -> commit или компенсация), отличие -
связь с исходным счетом и маркировка событий (`refund.completed` в типах
уведомлений мерчанту, архитектурный документ, раздел уведомлений).

Контракты payout не имели поля возврата: `CreatePayoutRequest`,
`Payout` и `PayoutEvent` расширены назад-совместимо (`refund_invoice_id`,
`cbl-protos` 5b3d1e0, buf breaking против CF-2 зеленый). Payout хранит маркер,
эмитит его в `payout.events`; проверка суммы (не больше возвращаемого остатка
счета) и REST `/v1/refunds` - Billing API 7.x (Payout не владеет счетами,
database-per-service); типы `refund.*` у мерчанта - Notification 8.x.

## 2. Границы

In scope: миграция `refund_invoice_id` (CHECK-формат, неизменяемость вторым
барьером), валидация и канонизация входа, включение маркера в `request_hash`,
проброс в `Payout`/`GetPayout` и `payout.events`, тесты unit/integration/e2e.

Out of scope: REST `/v1/refunds` и проверка остатка счета (7.x), типы `refund.*`
в Notification (8.x), частичные возвраты по одному счету агрегацией (7.x),
`invoice_id` в других сервисах (Payment/Quote), сторно-проводки (10.x).

## 3. Функциональные требования

FR-1. Контракт (аддитивно, CF-2-совместимо): `CreatePayoutRequest.
refund_invoice_id`, `Payout.refund_invoice_id`, `PayoutEvent.refund_invoice_id`
(`cbl-protos` 5b3d1e0). Пустое значение - обычная выплата; непустое - возврат.

FR-2. Валидация: непустой `refund_invoice_id` канонизируется как UUID
(регистр и форма приводятся к нижнему каноническому виду), невалидное значение
или нулевой UUID и строка из пробелов - `ErrInvalidPayoutInput`
(InvalidArgument) до создания выплаты; непустой маркер входит в `request_hash`
(повтор ключа с другим счетом возврата - конфликт тела), пустой маркер хэш не
меняет: идемпотентный повтор выплат, созданных до 10.6, остается валидным.

FR-3. Хранение: миграция 00005 добавляет `refund_invoice_id text` с CHECK
формата UUID (NULL - обычная выплата) и частичный индекс по значению;
`payouts_transition_guard` обновлен (CREATE OR REPLACE): маркер возврата
неизменяем после создания (наравне с суммами и адресом получателя).

FR-4. Сага: возврат проходит существующий путь 10.2 без изменений
(`requested -> reserved -> sent_to_gateway -> completed/failed ->
compensated`, ключи идемпотентности, привязка вердиктов); апрув 10.5
применяется по общей политике порогов.

FR-5. События: каждое событие возврата несет `refund_invoice_id`
(requested/approved/completed/failed/compensated); Notification 8.x по
непустому маркеру публикует типы `refund.*` вместо `payout.*` (реализация -
8.x); `GetPayout` возвращает маркер в `Payout` (`CreatePayoutResponse` по
CF-1 несет только идентификатор и состояние - маркер известен вызывающему из
запроса).

FR-6. Наблюдаемость: лог создания отличает возврат (без сумм и адресов:
payout_id, refund_invoice_id); runbook обслуживания возвратов.

## 4. Контракты

- gRPC: `CreatePayoutRequest.refund_invoice_id` (вход), `Payout.
  refund_invoice_id` (ответы Create/Get), CF-1 + аддитивные поля.
- Kafka: `PayoutEvent.refund_invoice_id` в `payout.events` (CF-2 +
  аддитивное поле); `payout.commands` не меняется (команда не знает о возврате).
- Хранилище: `payouts.refund_invoice_id` (миграция 00005).

## 5. Модель данных и миграции

```sql
ALTER TABLE payouts ADD COLUMN refund_invoice_id text
    CHECK (refund_invoice_id IS NULL OR refund_invoice_id ~ '^[0-9a-f]{8}-...');
CREATE INDEX payouts_refund_idx ON payouts (refund_invoice_id)
    WHERE refund_invoice_id IS NOT NULL;
CREATE OR REPLACE FUNCTION payouts_transition_guard() ... -- + неизменяемость маркера
```

Только вперед; существующие выплаты получают NULL (обычные).

## 6. Конечные автоматы и правила

Новых состояний и переходов нет: возврат использует автомат 10.1 и сагу 10.2
целиком. Отличие - маркер `refund_invoice_id`, неизменяемый вторым барьером.

## 7. Edge cases

Пустой маркер (обычная выплата); невалидный UUID (InvalidArgument до вставки);
регистр/форма UUID (канонизируется); повтор ключа с тем же телом (идемпотентно),
с другим счетом возврата (конфликт); невалидный UUID на прямом INSERT (CHECK);
смена маркера UPDATE-ом (immutable); возврат с апрувом (крупный - два
оператора); отказ/компенсация возврата (события `refund.*` с маркером);
несколько частичных возвратов по одному счету (несколько выплат с одним
маркером - допустимо, агрегация остатка - 7.x); возврат неизвестного счета
(Payout не проверяет существование счета - зона 7.x, документировано).

## 8. Нефункциональные требования

Изменения аддитивны и не меняют производительность саги; CHECK и индекс
дешевы; канонизация и валидация - до транзакции создания; логи без сумм.

## 9. План тестов

| Уровень | Сценарии |
| :-- | :-- |
| Unit (usecase) | валидация и канонизация UUID; маркер входит в `request_hash`; возврат проходит Advance; невалидный - без создания |
| Unit (transport) | проброс `refund_invoice_id` из запроса и в `Payout` ответа (Create/Get) |
| Integration | возврат: создание -> сага до completed с маркером в событиях requested/completed; неизменяемость маркера (триггер); CHECK-формат на INSERT |
| E2E | Kafka+PostgreSQL: возврат создается, команда уходит, submitted+confirmed -> completed; события завершения несут `refund_invoice_id` |
| Load | 14.1 |

Целевое покрытие unit+integration: не ниже 80%.

## 11. Открытые вопросы и решения

- Возврат представлен полем `refund_invoice_id`, а не отдельным типом payout:
  автомат и сага общие (`CBL-000`: «частный случай выплаты»), отдельный вид
  добавил бы состояниев и ветвлений без пользы; Notification различает типы по
  маркеру.
- Проверка суммы возврата (остаток по счету) - Billing API 7.x: у Payout нет
  данных о счетах (database-per-service); Payout доверяет сумме вызывающего в
  рамках общих лимитов.
- Несколько частичных возвратов по одному счету агрегируются на стороне 7.x;
  Payout хранит маркер и допускает несколько выплат с одним счетом.
- Возврат на произвольный адрес - как у выплаты (адрес задает мерчант);
  комплаенс-проверки - 13.x.
- `refund.*` вебхуки мерчанту - 8.x (в CBL-003 раздел 4 зафиксированы
  `refund.completed` и `refund.failed`; решение по `refund.compensated` -
  владелец контракта на CF-3).
- Payout не проверяет существование и владельца `refund_invoice_id` и остаток
  по счету (нет данных, database-per-service): при неаутентифицированном
  `CreatePayout` участник доверенной сети может инициировать `refund.*` с
  произвольным счетом (KI-payout-02); проверка остатка и владения обязательна
  в Billing API 7.x, до этого - общий запрет prod (0.5/0.6).

## 12. Ревью (CBL-001, шаг 6)

Четыре независимых прохода (15.10.2026). Блокеров безопасности нет: второе
барьерное тело триггера не ослаблено (immutable-поля, reserve_id, версия,
матрица, терминальные идентичны 00001, добавлена только неизменяемость
маркера), канонизация UUID согласована с CHECK. BLOCKER закрыты:
детерминированность e2e-шага возврата (ожидание события по payout_id и типу
вместо чтения первых записей топика); регрессия `request_hash` (пустой маркер
больше не меняет хэш - повтор выплат до 10.6 идемпотентен; golden-тест формата).
MAJOR закрыты: Down миграции 00005 восстанавливает прежнее тело триггера
(проверено на PostgreSQL); аддитивные контракты зафиксированы тегом
`cbl-protos@cf-2.1` и журналом cbl-protos; спеки выровнены (маркер в
`GetPayout`; `CreatePayoutResponse` без `Payout`); логи отличают возврат
(`refund_invoice_id`, без сумм); `uuid.Nil` и строки из пробелов отклоняются;
транспортный тест проверяет проброс маркера во вход саги; integration
ассертит CHECK-констрейнт; e2e-скрипты используют `-ge` к версии миграций.
AGENTS.md и CBL-003 обновлены в этом коммите (T-PAYOUT-09, KI-payout-02,
runbook возвратов). Принято без изменений: частичный индекс `payouts_refund_idx`
как задел для 7.x/12.x (холодный), `CREATE INDEX` без CONCURRENTLY (стенд),
UUIDv7 не требуется (принимается любой валидный UUID - счета приходят из 7.x).
