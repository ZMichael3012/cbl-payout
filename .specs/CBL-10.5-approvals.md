# CBL-10.5. Лимиты и двухэтапное подтверждение крупных выплат

| Поле | Значение |
| :-- | :-- |
| Эпик | E10, Payout/Refund Service (Saga) |
| Репозиторий | `cbl-payout` |
| Размер | M |
| Волна и параллельная группа | W2-PAYOUT |
| Зависит от | 10.1 |
| Версия контрактов | `cbl-protos@cf-2` (`billing/payout/v1` ApprovePayout, CF-1) |
| Статус | done, ревью закрыто |

## 1. Контекст и цель

Крупные выплаты требуют ручного подтверждения оператора по пороговой сумме
(`CBL-000` раздел 5; источник: архитектурный документ, админ-маршрут
`POST /admin/v1/payouts/{id}/approve` и `/reject`). Задача вводит:

- политику порогов апрува по активу и сумме (`PAYOUT_APPROVAL_POLICY`) - ниже
  порога выплата мала и не требует ручного подтверждения, выше - требует
  **двух операторов** (двухэтапность: правило двух человек, а не два шага саги);
- gRPC `ApprovePayout` (CF-1): запись голоса оператора и, при наборе порога,
  переход `requested -> approved`; отклонение - `requested -> rejected`;
- журнал голосов `payout_approvals` (append-only, аудит и идемпотентность
  повторов по оператору).

Гейт в `CreatePayout` (малая выплата идет в сагу без апрува) подключается в
10.2, где появляется сам `CreatePayout`; 10.5 поставляет политику, сервис
апрува и RPC.

## 2. Границы

In scope: доменная политика порогов (`ApprovalPolicy`), миграция
`payout_approvals`, storage-методы (locking read, голоса, tx-раннер), usecase
`ApprovalService`, gRPC-обработчик `ApprovePayout` и обвязка `main`, тесты
unit/integration/e2e (grpcurl на compose).

Out of scope: `CreatePayout`/`GetPayout` (10.2), запуск саги после апрува
(резерв) - 10.2, сама кнопка оператора в Back-office (12.2), RBAC/аудит
админского контура (12.1), GetPayout для оператора (10.2).

## 3. Функциональные требования

FR-1. Политика `PAYOUT_APPROVAL_POLICY` (JSON): ярусы требований по активу,
`{"USDT":[{"below_minor":1000000,"approvals":0}],"default":2}`. Первый ярус, где
`amount < below_minor`, задает требуемое число операторов; иначе `default`
(по умолчанию 2 - fail-safe: без настройки крупные выплаты не проходят без
двух операторов). Разбор строгий: `below_minor` и `approvals` обязательны
(отсутствие, `null`, неизвестные поля и опечатки - ошибка), активы в верхнем
регистре 2 - 16 символов, дубликаты отклоняются, `approvals` 0 - 10, `default`
0 - 10; пустая строка - значения по умолчанию. Нулевое значение структуры
политики («не сконфигурирована») трактуется как fail-safe 2, явный
`"default":0` - легальное решение оператора. На границе яруса
(`amount == below_minor`) действует следующий ярус. Невалидная конфигурация -
сервис не стартует (exit 1); эффективная политика логируется
(`ApprovalPolicy.Describe`).

FR-2. Миграция `payout_approvals` (append-only): `id bigserial`, `payout_id`
(FK), `operator_id` (формат `^[A-Za-z0-9._:@-]{1,128}$` - контракт идентичности
оператора 12.1), `approve boolean`, `reason` (до 255, без управляющих символов),
`required` (1 - 10, аудит требований на момент голоса; 0 - «апрув не нужен» -
голос не пишется), `created_at`; уникальность `(payout_id, operator_id)` -
повторный голос того же оператора идемпотентен и не считается дважды, префикс
уникального индекса покрывает выборки по `payout_id`; триггеры append-only
(UPDATE/DELETE/TRUNCATE).

FR-3. `ApprovePayout` (usecase `ApprovalService.Approve`): вход - payout_id,
operator_id, approve, reason. Условия (порядок проверок фиксирован):
- выплата не найдена - `storage.ErrNotFound`;
- оператор вне формата/лимитов, причина с управляющими символами или
  отклонение без причины - `ErrInvalidApprovalInput`;
- повтор оператора с другим решением - `ErrVoteLocked` (решение неизменяемо,
  append-only; вето задним числом невозможно);
- состояние не `requested`: повтор оператора, уже голосовавшего, - идемпотентный
  успех (текущее состояние), иначе `ErrPayoutDecided` (проверка состояния
  важнее порога: решенная выплата отвечает «уже решена»);
- состояние `requested`, требуемое число 0 - `ErrApprovalNotRequired` (голос не
  записывается);
- `approve=false` - голос и переход `requested -> rejected` (reason в
  `failure_reason` и журнал перехода); одного отклонения достаточно;
- `approve=true` - голос; при наборе `required` различных операторов выплата
  переходит `requested -> approved`; повтор с тем же решением пересчитывает
  порог по текущей политике (снижение `required` между голосами завершает
  выплату), но состояние само по себе не меняет.

FR-4. Транзакционность и конкурентность: голос и переход (при наборе) - одна
транзакция; перед подсчетом голосов выплата читается под row-локом
(`PayoutForUpdate`); переход - `TransitionTx` с CAS; конфликт версии откатывает
попытку целиком (голос не фиксируется) и повторяется до 3 раз, затем ошибка
(в транспорт - `Aborted`). Два одновременных голоса разных операторов дают
ровно один переход в `approved` при `required=2`. Порядок блокировок
(`payouts` -> `payout_approvals`) фиксирован для будущей outbox-эмиссии 10.2.

FR-5. gRPC `ApprovePayout` (transport): маппинг ошибок - `ErrNotFound` ->
`NotFound`, `ErrInvalidApprovalInput` -> `InvalidArgument`, `ErrPayoutDecided`/
`ErrApprovalNotRequired`/`ErrVoteLocked` -> `FailedPrecondition`,
`context.Canceled`/`DeadlineExceeded` -> одноименные коды, конфликты после
повторов -> `Aborted`, прочее -> `Internal`; успех возвращает `Payout` (CF-1).
`CreatePayout`/`GetPayout` до 10.2 отвечают `Unimplemented`.

FR-6. Обвязка `main`: репозиторий, `ApprovalService` и регистрация
`PayoutService` на gRPC-сервере; разбор и лог политики при старте; фатальные
ошибки старта (нет DSN, миграции, конфигурация, порт) завершают процесс с
кодом 1 (`fatal`) - оркестратор видит неуспех.

## 4. Контракты

- gRPC: `billing.payout.v1.PayoutService.ApprovePayout`
  (`ApprovePayoutRequest{payout_id, operator_id, approve, reason}`,
  CF-1, `cbl-protos@cf-2`); `Payout.state`, `state_version`, `failure_reason` -
  как в 10.1.
- HTTP-периметр (`/admin/v1/payouts/{id}/approve`) - Back-office 12.2 через
  этот RPC; 10.5 периметр не поднимает.
- Событие `payout.events` `payout.approved` из перехода - 10.2 (outbox-эмиссия
  появится вместе с сагой; текущая задача переходы пишет в журнал).
- Переменная окружения: `PAYOUT_APPROVAL_POLICY` (JSON, см. FR-1).

## 5. Модель данных и миграции

Миграция `00004_payout_approvals.sql` (только вперед):

```sql
payout_approvals(id bigserial, payout_id uuid REFERENCES payouts(id),
                 operator_id text, approve boolean, reason text,
                 required int, created_at timestamptz,
                 UNIQUE (payout_id, operator_id))
```

Плюс триггеры append-only (образец 10.1). Существующие данные не
переписываются: `requested`-выплаты без голосов остаются в ожидании апрува.

## 6. Конечные автоматы и правила

Новых состояний нет: используется `requested -> approved | rejected` из матрицы
10.1. `rejected` - терминальный (одно отклонение); `approved` - вход саги 10.2.
Двухэтапность - правило двух операторов (`required >= 2`), а не промежуточное
состояние: пока голосов меньше требуемого, выплата остается `requested`.

## 7. Edge cases

Голос без предшествующего создания (не найдена); повторный голос того же
оператора с тем же решением (идемпотентно, одна строка; порог пересчитывается
по текущей политике); повтор с другим решением (решение неизменяемо -
`ErrVoteLocked`, вето задним числом невозможно); голос после решения
(идемпотентно для голосовавшего, `ErrPayoutDecided` иначе, в том числе при
текущем пороге 0); отклонение после одного апрува (разными операторами -
rejected; повторное отклонение тем же - идемпотентно); набор `required` из
одного оператора повторно (не считается); `required=0` (голос отклоняется,
состояние не меняется); пустой/сверхдлинный/непечатаемый `operator_id`,
reason длиннее 255 или с управляющими символами, отклонение без причины;
конкурентные голоса (row-lock: ровно один переход при пороге); гонка двух
вызовов одного оператора (unique + сверка решения); гонка с сагой после
`approved` (повтор голоса - идемпотентный успех по строке голоса); политика
меняется между голосами (в `required` зафиксировано значение на момент голоса,
решение - текущей политикой); выплата терминальная (completed/compensated) до
голоса - `ErrPayoutDecided`; конфликт CAS откатывает попытку целиком (голос не
фиксируется); конфликт после 3 попыток - `Aborted` (повтор клиентом).

## 8. Нефункциональные требования

Транзакция голоса: locking read + insert голоса + возможный переход; внешних
вызовов нет; число записей на вызов - 6 - 8; дедлайн ApprovePayout (CF-1, 2 с)
укладывается; логи: Debug на записанный голос (payout_id, operator_id,
approve, required), Info на переход (state, version), без сумм и адресов.

## 11. Открытые вопросы и решения

- Двухэтапность = два разных оператора (источник: архитектурный документ,
  админ-маршрут апрува): уникальность `(payout_id, operator_id)` делает правило
  структурным, повторный голос идемпотентен. Отклонение одним оператором
  достаточно (вето). Решение оператора неизменяемо (append-only): смена
  решения отклоняется `ErrVoteLocked`, вето задним числом через повтор
  невозможно.
- Идемпотентность `ApprovePayout` без `idempotency_key` в CF-1: повторная
  доставка вызова тем же оператором - успех по строке голоса; отсутствие ключа
  зафиксировано в AGENTS (KI-payout-09), расширение контракта - вопрос
  владельца CF.
- Политика меняется между голосами: `required` в строке голоса - аудит на
  момент, решение о переходе принимается по текущей политике и числу строк;
  повтор голоса пересчитывает порог, поэтому снижение `required` завершает
  выплату без нового оператора.
- Дрейф порога вниз после создания (крупная стала малой): голос вернет
  `ErrApprovalNotRequired`, сага такую `requested`-выплату не подхватывает -
  обязанность 10.2 - re-gate `requested` по текущей политике при создании
  и/или фоновом восстановлении (10.2/10.7).
- Гейт в `CreatePayout` (малая сумма без апрува, крупная - в ожидание) и
  возобновление саги после `approved` - 10.2; 10.5 не поднимает сагу.
- `rejected` не имеет события в CF-2 (`payout.events` типы без rejected):
  Notification об отказе оператора - вопрос 12.2/8.x (зафиксировано в 10.1,
  T-PAYOUT-04).
- RBAC оператора (кто вправе апрувить) - 12.1/12.2; здесь проверяется только
  формат и уникальность идентификатора оператора. До mTLS/authN (0.5/0.6)
  любой участник доверенной сети может набрать кворум произвольными
  operator_id (KI-payout-02).
- Back-office (12.2) не увидит прогресс апрува по CF-1 `Payout` (нет числа
  голосов): read-контур голосов - расширение контракта или отдельный RPC
  владельца CF при 12.2.

## 12. Ревью (CBL-001, шаг 6)

Четыре независимых прохода (15.10.2026). BLOCKER закрыты: fail-open разбор
